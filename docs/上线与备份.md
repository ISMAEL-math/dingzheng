# 邀请内测版：账号、数据与部署

## 当前支持边界

这是单实例内测部署方案：Node 24.14+（24.x）、SQLite、一个持久化数据卷。不要运行多个应用副本，也不要让两个版本同时写同一数据目录。数据库 schema 版本为 1；未来升级需提供迁移，旧程序遇到更高版本会拒绝写入。

默认 `APP_MODE=local` 仍只监听回环地址，无需账号。`APP_MODE=hosted` 必须配置 HTTPS 的 `PUBLIC_ORIGIN`，所有业务 API 都要求登录并检查来源。公网前端使用反向代理，禁止直接暴露 Node 端口。托管模式不共享开发者的本机 ChatGPT 登录，使用 API 模型服务。

账号由管理员创建，没有公开注册接口。密码使用带随机盐的 scrypt；会话使用 HttpOnly、Secure、SameSite=Strict Cookie，有效期七天。退出、禁用账号或重置密码会撤销对应会话。登录有 IP 频率限制；反向代理后该限制是共享出口限制，适合小规模内测，大规模时需单独调整可信代理与限流。

## 数据保存和首次迁移

- 浏览器学习记录、设置、照片及上传 PDF 通过 `/api/storage` 保存到 `DATA_DIR/workspace.sqlite`，不再依赖浏览器长期保留。数据值使用 AES-256-GCM 加密，密钥在 `DATA_DIR/storage.key`；数据库与密钥必须一起备份。服务端管理员仍拥有解密能力，这不是端到端加密。
- 本机首次刷新自动迁移旧 IndexedDB 的 `workspace` 和 `pdfFiles`，先迁移原件、最后写入学习记录，原浏览器数据库保留。中断后可重试。不要在迁移完成前清理浏览器。
- 多用户教材保存在 `DATA_DIR/users/<内部用户ID>/textbook-library`。本机原教材目录 `DATA_DIR/textbook-library` 保留。
- 托管账号不会自动读取当前浏览器旧本机数据库，避免共用设备串号。需要迁移既有资料时，由管理员做明确的数据导入，或使用原有学习记录导入功能并重新上传原件。
- 多设备/多标签页采用乐观版本检查。收到“另一页面或设备已更新”时，当前保存没有覆盖远端；先记录未保存输入，再刷新。暂不支持自动合并或离线编辑。
- API 单次数据事务最大 300 MB（含 Base64 文件编码）。普通 PDF 保持原有 200 MB 上限。SQLite 大对象和整份学习状态适合初期规模；后续扩展应拆分记录和对象存储。

## 创建和管理账号

```sh
# 默认 .local；生产命令须指向实际持久化目录
DATA_DIR=/path/to/data npm run accounts -- create alice
DATA_DIR=/path/to/data npm run accounts -- list
DATA_DIR=/path/to/data npm run accounts -- reset-password alice
DATA_DIR=/path/to/data npm run accounts -- disable alice
```

创建和重置时通过终端的隐藏输入提供至少 12 字符密码。非交互环境从标准输入读取；不要把密码写进命令参数或 Git。

## 本机完整备份与恢复

页面的“导出学习记录 JSON”仍可用于迁移记录，但不包含全部原件。完整备份由管理员操作，覆盖数据目录内的学习记录、PDF、教材解析、账号、密钥与本机连接状态。

1. 先刷新应用完成首次数据迁移，确认页面角落显示“服务端保存”。
2. 停止服务。不要在正在解析/批改时停机；等待任务完成或主动暂停。
3. 创建并验证备份：

```sh
node scripts/backup.mjs create .local /absolute/path/to/backups/release-001
node scripts/backup.mjs verify /absolute/path/to/backups/release-001
node scripts/backup.mjs restore /absolute/path/to/backups/release-001 /absolute/path/to/restored-data
DATA_DIR=/absolute/path/to/restored-data npm start
```

备份脚本检查运行锁，复制后生成 SHA-256 文件清单；恢复前逐文件验证，只恢复到不存在的新目录，拒绝覆盖现有数据、符号链接和路径越界。恢复后检查账号登录、资料数量、至少一份 PDF 和一道关联题，再切换生产数据目录。旧目录保留至验收。

备份包含敏感凭证，请保存在受控目录并复制到另一台机器或受控备份服务。脚本不会自动上传，也不代表已配置异地备份。`.env` 和外部代理配置不在数据目录中，需单独私密保存。退出异常后遗留运行锁只有在确认原进程不存在时才能处理。

## 构建和发布

```sh
# 并行 agent 的修改全部提交后，从确定的 Git 提交构建
npm run release
cp deploy/.env.example deploy/.env
# 编辑 APP_IMAGE 为输出的 dingzheng:<完整提交SHA>
# 设置 PUBLIC_ORIGIN=https://实际域名 和所需模型服务密钥

docker compose --env-file deploy/.env -f deploy/compose.yaml up -d
```

镜像以最终 Git 提交为固定标签，`APP_VERSION` 写入镜像；数据使用独立命名卷，不随容器替换。Caddy 示例在 `deploy/Caddyfile`，部署在宿主机时反向代理到 `127.0.0.1:4173`，配置真实域名和 HTTPS。需要先准备 DNS、证书和主机；本次未自动开通任何公网资源。

账号在运行容器中管理：

```sh
docker compose --env-file deploy/.env -f deploy/compose.yaml exec app node scripts/accounts.mjs create alice
```

每次发布后核对 `/healthz`、`/readyz` 的 `version` 与目标提交相同，再验收登录、读取资料、保存、退出重登。页面角落也显示版本。容器在进程退出时自动重启；healthcheck 的 unhealthy 状态本身不会自动重启，需要监控告警或运维处理。模型上游服务不作为就绪条件，避免上游故障导致容器重启循环。

CI 会执行完整测试并构建容器；当前环境未运行 Docker daemon 时，只能验证 Node 服务和配置，不能声称已完成镜像运行验收。

## 容器中的完整备份

先停止 app，再使用相同卷进行一次性备份。`BACKUP_DIRECTORY` 是宿主机已创建且容器 node 用户可写的私密目录，备份目录名称必须全新：

```sh
docker compose --env-file deploy/.env -f deploy/compose.yaml stop app
docker compose --env-file deploy/.env -f deploy/compose.yaml run --rm --no-deps \
  -v /absolute/BACKUP_DIRECTORY:/backup app node scripts/backup.mjs create /data /backup/release-001
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d
```

容器 PID 命名空间可能复用旧 PID；正常停止会清除运行锁。异常停止遗留锁必须确认没有其他实例使用该卷后再清理。

## 回滚

1. 记录当前版本与数据备份。
2. 将 `deploy/.env` 的 `APP_IMAGE` 改回已验证的上一提交镜像。
3. 执行同一条 `docker compose ... up -d`，核对健康接口与页面版本。
4. 只有数据 schema 兼容时才能仅回滚程序；不兼容时，先按上述恢复流程恢复到新的数据目录/卷，再切换。不能用旧程序盲写升级后的数据。

## 并行开发约定

每个 agent 使用独立分支和 worktree；不要边编辑共享目录边把它当发布目录。合并后只从干净提交发布；`release.sh` 会拒绝未提交改动。本次脚本不会重置、暂存或覆盖其他 agent 的工作。
